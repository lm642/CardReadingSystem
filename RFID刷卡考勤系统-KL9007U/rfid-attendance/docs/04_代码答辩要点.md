## 一、RFID 读卡通信原理（对应 20 分）

### Q1. 你们用的是什么读卡器？怎么和它通信？
**结论**：KL9007U 超高频(UHF)读写器，USB 转虚拟串口，程序通过串口主动发命令读卡。

- 通信方式：读写器经 USB 转串口芯片（CP210x/CH340）在系统里表现为一个 **COM 口（COM9）**，
  上位机用 `pyserial` 打开该串口收发字节。**不是**键盘模拟（HID）那种直接吐字符串。
- 代码：`uhf_reader.py: UHFReader18.open()` → `serial.Serial(port, baud, timeout=0.1)`

关键点（会加分）：**这台是 UHF 读写器，工作在"应答模式"**，它不会主动把卡号打到串口上。
必须由程序发"询查命令"，它才回数据。这就是为什么不能直接读串口、必须先实现协议。

### Q2. 波特率是多少？还有哪些串口参数？
**结论**：57600 bps，8 数据位，1 停止位，无校验（8N1）。

- 代码：`UHFReader18.__init__(baud=57600)`；默认值在 `attendance.py: DEFAULT_SETTINGS["serial_baud"]="57600"`。
- 可改：`0x00=9600 0x01=19200 0x02=38400 0x03=57600 0x04=115200`（命令 `0x20`）。

### Q3. 通信帧的格式是什么？
**结论**：命令帧 `Len | Adr | Cmd | Data[] | CRC-L | CRC-H`，响应帧多 `reCmd` 和 `Status`。

- `Len` = Data 长度 + 4（**不含 Len 本身**）；
- `CRC16`：多项式 `0x8408`，初值 `0xFFFF`，**低字节在前**，校验范围「Len → Data」；
- 代码：`build_command()` 组帧、`crc16()` 算校验、`split_frames()` 切帧。

**可直接背的例子**（现场能画出来很加分）：
- 询查命令（读 EPC）：`04 00 01 DB 4B`
- 读读写器信息：`04 00 21 D9 6A`

### Q4. 卡号是怎么编码的？16 进制还是字符串？
**结论**：读写器回的是**二进制字节**，我们把 EPC 字节按**十六进制**转成字符串当卡号。

- 例：读写器回 EPC 6 字节 `00 11 58 23 00 00` → 卡号字符串 `"001158230000"`。
- 代码：`parse_inventory_payload()` 里 `payload[pos:pos+l].hex().upper()`。
- 为什么用十六进制而不是转十进制：**所见即所得**，不做进制换算就不会引入误差，
  同一张卡每次都得到同一个字符串，绑定和匹配才可靠。

### Q5. 原始数据是怎么解析的？（这是答辩重点）
**结论**：两步——先"切帧"，再"解包"。

1. **切帧** `split_frames(buf)`：串口是"字节流"，可能粘包（两帧连一起）或半包。
   做法：取首字节当 `Len`，整帧 = `1+Len` 字节；再用 CRC 校验；
   校验不过就后移一字节重新找帧头（重新同步）。→ 解决粘包/半包/脏字节。
2. **解包** `parse_inventory_payload(payload)`：响应 Data 段 =
   `[标签个数 Num][EPC长度][EPC][EPC长度][EPC]…`，按长度前缀逐个取出 EPC。
   （同时兼容 `[Num][EPC]` 的简化固件格式。）

### Q6. 脏数据过滤逻辑在哪？
**结论**：三道防线。

| 防线 | 做什么 | 代码 |
|---|---|---|
| ① 帧层 | 帧长非法 / CRC 不过 → 丢弃 | `split_frames()` |
| ② 卡号层 | 去控制符、去分隔符、统一大写；非 4~32 位十六进制 → 丢弃 | `normalize_card()` / `is_valid_card()` |
| ③ 业务层 | 重复卡、陌生卡、非法文本 → 不写有效记录 | `AttendanceService.handle_card()` |

## 二、业务与数据库逻辑（对应 15 分）

### Q7. 数据库有哪几张表？主键怎么设计的？
**结论**：4 张表，见 `attendance.py: SCHEMA_SQL`。

| 表 | 主键 | 说明 |
|---|---|---|
| students | `id` 自增代理主键 + `student_no` 业务主键(UNIQUE) | `card_no` 也加 UNIQUE，一张卡只能绑一个学生 |
| attendance | `id` 自增代理主键 | 记录打卡；冗余学号/姓名/班级**快照** |
| unknown_cards | `id` | 陌生卡留痕 |
| settings | `key`（主键） | key-value 配置 |

**为什么用代理主键而不是学号直接当主键**：学号可能变更，且整型自增主键在建索引、
做外键关联时更高效、更稳定；学号用 UNIQUE 约束保证业务唯一。

**为什么 attendance 里冗余学生信息**：即使学生被改名或删除，历史记录依然完整可读（快照）。

### Q8. 怎么判断这次刷卡是"签到"还是"签退"？
**结论**：查该学生**当天最后一条记录**，再结合时间差判定。

代码 `AttendanceService.handle_card()` 的逻辑：
```
当天无记录                 -> 签到(in)
当天最后一条是 签到(in)：
   距今 >= 30 分钟         -> 签退(out)
   距今 <  30 分钟         -> 拒绝(TOO_SOON)
当天最后一条是 签退(out)    -> 重新签到(in)   // 允许一天多轮进出
```
关键查询：`Database.latest_record_of_day()`：
```sql
SELECT * FROM attendance
WHERE student_id = ? AND day = ?
ORDER BY ts DESC, id DESC LIMIT 1;
```
注意 `ORDER BY ts DESC, id DESC`——同一秒内的两条记录靠自增 id 再排一次，保证稳定。

## 三、现场代码修改能力（对应 5 分，杀手锏）

### Q9. 现场要求：签到签退间隔不少于 30 分钟，怎么改？
**结论**：**不用改代码**——这本来就做成了配置项。

- 数据存在 `settings` 表，键 `interval_minutes`，默认 `"30"`（见 `DEFAULT_SETTINGS`）。
- 界面上：【设置】页 →「签到签退最小间隔（分钟）」→ 改数值 → 保存即可。
- 代码里用 `self.db.get_float("interval_minutes", 30.0)` 读取，判定处：
  ```python
  delta_min = (now - parse_ts(last["ts"])).total_seconds() / 60.0
  if delta_min < interval:      # interval 来自设置
      return Result(False, "TOO_SOON", ...)
  ```
- 若要改**默认值**：把 `DEFAULT_SETTINGS["interval_minutes"]` 改成想要的值即可。

> 讲解话术：把"业务规则"抽成了配置项，规则变化不改代码，这是为可维护性做的设计。

### Q10. 如果要求"间隔改成 45 分钟"，并在代码里体现为硬规则呢？
两处任选其一：
1. 改默认值：`DEFAULT_SETTINGS["interval_minutes"] = "45"`；
2. 或把判定写死：`if delta_min < 45:`。

### Q11. （加试）如果要再增加"每天最多允许签退一次"呢？
思路：在判定 `out` 之前，先查当天 `action='out'` 的记录条数，≥1 就拒绝。
```python
cnt = self.db.conn.execute(
    "SELECT COUNT(*) c FROM attendance WHERE student_id=? AND day=? AND action='out'",
    (stu["id"], day)).fetchone()["c"]
if action == "out" and cnt >= 1:
    return Result(False, "TOO_SOON", "今日已签退过", ...)
```
说明你知道"业务规则如何落到 SQL"——这是评委最想看到的。

## 四、异常处理（评分表"异常场景处理"10 分）

| 评委问 | 答 |
|---|---|
| 陌生空白卡怎么办？ | 查不到绑定 → 返回 `UNKNOWN`，界面友好提示，写入 `unknown_cards` 留痕，**程序不崩**（`handle_card`） |
| 短时间连续重复刷卡？ | 读卡层去抖：同卡在 `debounce_seconds` 内只上报一次，且命中时**续期**（卡不拿走就一直忽略）；业务层再判一次 `DUPLICATE` |
| 读卡器 USB 拔掉？ | 串口读写抛异常 → `CardReaderThread.run()` 捕获 → 提示并每 `reconnect_seconds` 秒自动重连，界面照常可用，不闪退 |
| **依赖装错解释器**（真实踩过的坑）？ | 见下面 Q12 |

## 五、真实踩坑记录（评委会感兴趣，讲出来是加分项）

### Q12. 我明明 `pip install pyserial` 了，程序却提示"未安装"，为什么？

**现象**：程序启动后设备状态显示红色「未安装 pyserial，已降级为键盘模式」，串口下拉框也点不动。

**排查过程**（这就是软件工程里的"定位问题"能力，值得讲）：

1. 先怀疑没装 → 命令行验证：
   ```
   python -c "import serial; print(serial.__version__, serial.__file__)"
   ```
   结果是 `3.5`，**确实装了**。
2. 那就怀疑"装的"和"跑的"不是同一只 Python → 列出这台电脑上所有解释器：
   ```
   py -0p
   ```
   发现装了 **3.10 / 3.12 / 3.13 / 3.14 四只 Python**。
3. 逐个检查谁有 pyserial：
   ```
   py -3.12 -c "import serial"      # 有
   py -3.13 -c "import serial"      # 有
   py -3.14 -c "import serial"      # 没有 ← 而 py 启动器默认指向它
   ```
   **根因**：`pip install pyserial` 装进了 3.12/3.13，但程序是被 3.14（或另一只）启动的。
   Python 的包是**按解释器隔离**安装的，换一只解释器就"看不见"之前装的包。

**解决方案**（讲这里最能体现工程能力）：

| 方案 | 评价 |
|---|---|
| 每次运行前手动 `pip install` 到正确解释器 | ❌ 依赖用户记忆，换台机器又出问题 |
| 写死一个 Python 绝对路径启动 | ❌ 换机器路径就失效 |
| **把 pyserial 内置进项目（vendoring）** | ✅ 采用这个 |

具体做法：把 pyserial 的源码（纯 Python、无 C 扩展）复制到项目 `_vendor/serial/`，
然后在导入处加"兜底重试"：

```python
def _import_serial():
    for use_vendor in (False, True):          # 先系统安装的，再项目内置的
        if use_vendor:
            sys.path.insert(0, VENDOR_DIR)    # 把 _vendor 挂到搜索路径最前面
        try:
            import serial
            return serial
        except Exception:
            continue
    return None
```

**一句话结论**：Python 依赖是**按解释器隔离**的，"装了" ≠ "跑的时候用上了"。
把关键依赖随项目一起分发（vendoring），是避免机房/评委电脑环境差异最稳的做法。
项目里的 `env_check.py` / `环境自检.bat` 就是专门用来看清"到底哪只 Python 缺什么"的工具。

## 六、可能被追问的细节（准备一下）

1. **CRC 怎么算的？** 初值 0xFFFF，逐字节异或后右移 8 次，最低位为 1 就异或 0x8408，最后低字节在前。见 `crc16()`。
2. **为什么要按 15ms 内发完一帧？** 协议规定相邻字节间隔超过 15ms 会被读写器当无效数据丢弃，所以用串口一次性 `write` 整帧。
3. **为什么询查要循环发？** 标签进入射频场才被读到，且读写器每次询查有"询查时间"，所以后台线程按 `poll_interval` 循环发。
4. **EPC 和 TID 有什么区别？** EPC 可被改写、用于业务标识；TID 出厂唯一、通常只读，防伪性更强。设置项 `use_tid` 可切换。
5. **为什么界面不直接读串口？** tkinter 不是线程安全的，串口读取会阻塞；所以放后台线程，结果经 `queue` 回传主线程（生产者-消费者）。
6. **`_vendor` 目录会不会影响评分（AI 代写）？** 不会，它只是一份第三方库源码；真正要讲清的是上面 Q12 的排查思路和 `_import_serial()` 的兜底逻辑。
7. **怎么证明这套代码真的能读卡？** 答辩前先跑 `环境自检.bat`（证明环境 OK）→ `读卡测试.bat`（证明硬件能读到卡、打印出 EPC），两步都有屏幕输出可存档。
